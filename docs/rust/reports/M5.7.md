# M5.7 Power menu overlay with two-step confirm and hardware-key navigation
Status: done on the host (core tests with fixture key events, shell unit tests, 4 new goldens inspected by eye); not yet on the tablet
Files changed: crates/walpad-proto/src/{command,lib}.rs (`ShellInput`, `power_menu` command), crates/walpad-core/src/{brain,daemon}.rs, crates/walpad-core/tests/live.rs, crates/walpad-shell/src/{app,app/tests,core_client,overlay,settings_screen,shell}.rs, crates/walpad-shell/tests/screens_snapshots.rs, crates/walpad-shell/tests/golden/power_menu_* (4 new) + power_confirm_* and settings_maintenance (regenerated: the Maintenance page gained a row)
What works now:
 - Core: when a client has subscribed to the `input` topic, a long power press publishes `{"event":"input","data":{"kind":"power_menu_open"}}` (also for the `powermenu` key action) and the Tk `walpad-powermenu.py` is NOT spawned. With no subscriber the old Tk path is unchanged.
 - While the shell's menu is open the core routes volume down/up (press only) as `volume_down` / `volume_up` and a short power press as `power_short` input events. Volume keys never reach the volume gestures meanwhile (no amixer), and a short power press does not toggle the screen. The core knows the menu state from the new `power_menu {open:bool}` command (the shell sends it on open and on every close) and expires its own routing after 25 s as a safety net if the shell dies; routing also stops when the shell's `input` subscription goes away.
 - Shell: `Overlay::PowerMenu` (Screen off, Restart, Shut down, Cancel; Cancel focused on open), drawn with `Painter::power_menu` (560 px sheet, centred). Volume down = next item, volume up = previous (both wrap), short power = activate focused item, touch taps use the same logic and move the focus. Screen off and Cancel act at once; Restart and Shut down need two activations: the first turns the button danger with "Tap again to shut down" (armed 3 s, same `POWER_ARM_MS` as the Maintenance dialog), a late second press only re-arms, arming a different item does not fire. The sheet closes itself 20 s after it opened (and tells the core). It also opens from Settings > Maintenance > "Power menu". Core loss closes it. Nothing is sent to the core for power actions while it is away.
 - New client plumbing: the shell subscribes to `status, wifi, input`; `CoreEvent::Input`; `App::take_cmds()` carries commands produced by the clock (the 20 s close).
Checks run: scripts/check.sh -> ALL CHECKS PASSED (see the M5.8 report for the final run, both cards share it). New tests: 3 brain unit tests (long press once, short press activates when the menu is open, volume keys become `ShellKey` only while routed and are gesture-free; normal volume gesture unchanged otherwise), 2 core integration tests with fixture event files and a real subscribed client (long power -> power_menu_open, volume down/up and short power arrive as events, screen not toggled, after `power_menu open:false` volume keys are ordinary again; without a shell nothing is published), 11 shell unit tests (open with Cancel focused + core notified, offline no-op, Settings action, focus wrap, activate Cancel / Screen off, two-step Restart and Shut down with expiry and late press, arming another item, touch taps, 20 s auto-close incl. `next_deadline`, core loss, 560 px geometry in both orientations), goldens `power_menu_cancel_{portrait,landscape}` and `power_menu_shutdown_armed_{portrait,landscape}` inspected by eye (focus ring on Cancel; armed Shut down red with "Tap again to shut down", Settings visible behind because the design has no scrim).

(3) A "Power menu" row was added to Settings > Maintenance as the "Settings action" (the existing Restart/Shut down dialogs there are untouched). (4) No scrim behind the sheet (design forbids transparency).
