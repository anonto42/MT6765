## What works now

### M9.1 log caps
- `walpad-logcap` (busybox sh, no dependencies). For each of `/var/log/walpad-*.log` (core, shell, session, wifi, devd, keys, touchd), `Xvfb.log`, `fbmirror.log`, `openbox.log`, `padui.log`, `dropbear.log`, `wpa_supplicant.log`: if larger than `WALPAD_LOG_MAX` (262144) it does: copy to `FILE.1` (atomic mv, previous generation), keep the last `WALPAD_LOG_KEEP` (65536) bytes without the cut first line, truncate IN PLACE with `: > FILE`, then `cat tail >> FILE`.
- Approach and why it is correct for running writers: the writer keeps its descriptor (same inode, no rename), and every writer now opens its log with `>>` (O_APPEND), so after the truncation its next write lands at the new end of file: no sparse hole. The scripts were changed accordingly: init (`dropbear`, `walpad-wifi`, `walpad-session`; `walpad-core` already used `>>`), session (`Xvfb`, `fbmirror`, `openbox`, `walpad-shell`), `walpad-python-daemons`. `wpa_supplicant -f` and padui (`>>` in walpad-rescue) already append. A test fails if any of those redirections goes back to `>`.
- Accepted race: lines written in the few ms between the copy and the truncate are in neither `FILE.1` nor `FILE`; a line written between the truncate and the restore lands before the restored tail. Worst case a handful of lines. Disk use per log is at most about 2 x MAX (current + `.1`) plus what is written between runs. Number of logs times 2 x 256 KiB is well under 5 MiB.
- Scheduling: init runs `walpad-logcap` once at start (logs persist on the ext4 across boots) and its final main loop is now `while true; do sleep ${WALPAD_LOGCAP_INTERVAL:-300}; walpad-logcap; done` (was `sleep 3600`). No new daemon; if init dies everything is gone anyway.
- Soak test (tests/shell/run.sh): one background writer holds a single `>>` descriptor and writes 12000 lines (about 1.08 MB, more than 1 MiB) while logcap runs every 0.1 s with MAX=100000, KEEP=20000. Result on host sh: 24 cap cycles, peak size seen before a cap 135390 (limit asserted: cap + slack 200000), final 47574, the last line (`soak done`) and the last numbered line (11999) survive, no NUL bytes (no sparse hole), `.1` exists. Same test passes on Alpine 3.24 busybox (25 cycles, peak 135390, final 76002).

### M9.2 safe mode
- Rust: `walpad_hw::evdev::{EVIOCGKEY_96 = 0x80604518, KEY_BITMAP_BYTES = 96, key_bit(bitmap, code), read_key_bitmap(path)}` (ioctl on character devices, O_NONBLOCK so it never blocks; on a plain file the first 96 bytes are the bitmap, which is how the host tests run) and `walpad_hw::input::{key_device_name, parse_key, key_held(root, code)}` (device found by NAME via the existing discovery: volume keys on `mtk-kpd`, power on `mtk-pmic-keys`; the `/dev/input/eventN` node is created from major:minor if missing, since there is no udev that early). The bit parser is a pure function with unit tests (bit 2 of byte 14 = code 114, out-of-range = not held, the opcode constant is checked against `_IOC(READ,'E',0x18,96)`).
- `walpad-ctl key-held <name|code>`: `volumedown|volumeup|power` or 114/115/116; exit 0 held, 1 not held, 2 error or unknown device or unknown key (message on stderr). Needs no core, so it works before anything is started.
- `walpad-safemode-check` (sourced-free, small): runs `timeout 1 walpad-ctl-rs key-held 114`; exit 0 only when that returns 0; a missing binary, rc 1, rc 2, a crash or a timeout all mean "not held" (normal boot). Env hooks for tests: `WALPAD_CTL`, `WALPAD_SAFEMODE_KEY`, `WALPAD_SAFEMODE_TIMEOUT`. Both init variants call it. `walpad-ctl-rs` is the same Rust binary in both images (`build_rootfs.sh` installs the `walpad-ctl-rs` symlink in both modes; in the default image `walpad-ctl` is still the old shell script, which is why the `-rs` name is used).
- In `walpad-init` the check is the FIRST thing after the log directories exist (the key is only held for a few seconds after power-on; the first boot can spend minutes in `fc-cache` afterwards). In safe mode init writes `/run/walpad/safemode`, creates `/run/walpad-ok` so the ramdisk's 150 s check sees "healthy" and does NOT start a second padui on the same framebuffer, and starts `padui` from the rootfs (`/usr/local/bin/padui`, restart loop, log `/var/log/padui.log`). Dropbear SSH and Wi-Fi (`walpad-wifi`) still start; the core and the graphical session (and its restart loop) are inside `if [ -z "$SAFE" ]` and are skipped. Logcap keeps running.
- Owner procedure: see "Device checks pending".

### M9.3 reproducible build
- `scripts/build_rootfs.sh`: `ALPINE_REL=3.24` is the single variable; the container is `alpine:$ALPINE_REL` (was `alpine:latest`) and the repository URL is built from it; the build aborts if the container is not that release. 3.24 is what `alpine:latest` was today and what the flashed image uses.
- Outputs next to the image: `packages.txt` (`apk info -v | LC_ALL=C sort`, fails if empty), `files.txt`, `config-hashes.txt` (sha256, mode, path for every file the repo owns as installed: all of `config/rootfs`, the overlay files in no-Python mode, `dmlinear`/`padui`/`fbmirror`, the three Rust binaries), `release.txt` (release, container image digest, apk-tools version), `image.sha256`. The host-built static tools are built automatically with their own `build.sh` when missing (they are gitignored binaries). The per-host ssh key is added after the manifests, so the hashes do not depend on the builder's key.
- `mke2fs` now gets a fixed UUID, hash seed and `E2FSPROGS_FAKE_TIME` (and all mtimes in the tree are normalised to `SOURCE_DATE_EPOCH`, default 1700000000).
- tools/propshim: NOT built by build_rootfs.sh, on purpose. `libwpdprops.so` (committed in data/wifi/) is only an `LD_PRELOAD` shim of the legacy SD-card Wi-Fi flow (`scripts/mtk_stack_up.sh`, `wifi_assoc.sh`, `wifi_now.py`); nothing in `config/rootfs` or the rootfs image references it. Its `build.sh` needs host clang+lld and writes into `data/wifi/`, and I may not edit it. I checked that the source builds in a throwaway `alpine:3.24` container with `apk add clang lld` and the same flags (clang 22.1.3): it links, but the result (`9df610c4...`) does NOT match the committed binary (`a97d822b...`, built by an older toolchain), so replacing it would change a binary that nothing in this card needs. The committed binary is untouched.

## Deviations
- Safe mode padui is started by init itself (not by walpad-rescue) and `/run/walpad-ok` is created by init in safe mode: it is the only way to stop the unchanged ramdisk starting a second padui at 150 s. Cost: the marker no longer proves a healthy Rust shell in safe mode (the shell does not run then).
- The key check runs once, early. A key released before init starts is not seen.
- The ext4 image is not byte-reproducible (see above); only the manifests are. propshim is not built (not part of the image).
- tests/shell steps were inserted just before the final `exit $FAIL` (the end of the file), not after it.
