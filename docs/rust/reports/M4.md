# M4 Wi-Fi control through the supplicant socket
Status: done on the host (real datagram sockets against a fake supplicant); M4.4 needs the tablet
Files changed: crates/walpad-core/src/wpa/{mod,ctrl,parse,psk,manager,fake}.rs, crates/walpad-core/src/{daemon,main,lib}.rs, crates/walpad-core/tests/{wifi,wifi_ipc}.rs, crates/walpad-proto/src/command.rs, crates/walpad-ctl/src/lib.rs, scripts/device/m4_check.sh
What works now:
 - M4.1 control client: two datagram sockets bound at /run/walpad/wpa-<pid> and wpa-<pid>e (mode 0600), PING/ATTACH, 5 s request timeout, stale replies drained first, any transport error drops the client and the manager reconnects every 2 s (supplicant restart tested).
 - M4.2 scan: single flight (second call = busy), results on CTRL-EVENT-SCAN-RESULTS or after 10 s, `\xNN` escape decoding to bytes, UTF-8 lossy for display (hex of the bytes is the identity), duplicate SSIDs merged keeping the strongest, hidden SSIDs dropped, sorted by signal, security = WPA if flags have WPA/RSN, else WEP, else open.
 - M4.3 connect/forget/disconnect: SSID as hex, WPA2 passphrase turned into the 64-hex PSK with PBKDF2-HMAC-SHA1 (4096 rounds, SSID salt; matches the IEEE 802.11i vectors), only the derived key goes to the supplicant, open networks use key_mgmt NONE, 25 s timeout, wrong key detected from CTRL-EVENT-SSID-TEMP-DISABLED reason=WRONG_KEY, a failed new network is removed, other saved networks are ENABLEd again, SAVE_CONFIG then the config file is forced back to mode 0600. Existing SSIDs are updated, not duplicated.
 - IPC: wifi_scan/wifi_connect answer `accepted` at once; results arrive as `wifi` events (kind scan|connect|disconnected) for subscribers of the wifi topic; wifi_list_saved, wifi_disconnect, wifi_forget are immediate. Status model now carries ssid and signal_dbm from the supplicant.
 - walpad-ctl: `wifi-scan` (waits and prints), `wifi-connect <ssid> [--open]` (passphrase read from stdin, never argv), wifi-saved, wifi-forget, wifi-disconnect.
 - `walpad-core --fake` also starts the fake supplicant, so the host session and the future shell have a working Wi-Fi flow.
Checks run: scripts/check.sh -> ALL CHECKS PASSED. Tests: 5 parser tests, 2 PSK vector tests, 7 manager tests over sockets (scan, WPA2 connect asserting the passphrase never appears in any command sent, wrong key, open + timeout, saved/forget/validation, supplicant restart), 1 end-to-end IPC test, ctl tests for scan/connect/wrong password/no stdin.
Bug found by the tests and fixed: secrets of 5 and 13 characters were treated as WEP keys, which rejected valid 13-character WPA passphrases (e.g. "correct horse"). WEP is unsupported; the only accepted secrets are 8-63 characters or 64 hex digits (also tightened in walpad-proto validation).
Device checks pending (M4.4, owner): printf '%s\n' 'PASSPHRASE' | ssh root@<ip> sh -s -- 'SSID' < scripts/device/m4_check.sh   (or run it on the tablet and type the passphrase), then a cold boot and smoke.sh. The script checks scan, join, that the passphrase is in no argv/log, config mode 600, other networks still enabled, wifi-state COMPLETED, internet, and forgets the test network.
Known limits: walpad-wifi (bring-up, DHCP, reconnect loop) is untouched and still owns the radio; there is no radio on/off (a failed CONNSYS power-on latches until reboot). WEP and WPA3-SAE-only networks are not supported (SAE needs a different key_mgmt). Behaviour with the real wpa_supplicant and the MediaTek driver is unverified: the fake models the documented protocol only (e.g. the real supplicant may answer SCAN with FAIL-BUSY while scanning, which is treated as "results will come as an event").
