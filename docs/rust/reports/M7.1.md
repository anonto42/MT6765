## What the build mode does
`WALPAD_NO_PYTHON=1 scripts/build_rootfs.sh` (output defaults to `build/rootfs-nopython/`, never `build/rootfs/`; `WALPAD_ROOTFS_OUT` still overrides):
- Packages: drops `python3 python3-tkinter tk py3-xlib xdotool`. apk then also leaves out their orphans (tcl, readline, gdbm, mpdecimal, the -pyc packages): 14 fewer of 253 packages (239). `xdotool` was only used by walpad-keys.py/walpad-devd.py; the Rust core injects keys over XTEST (its "xdotool" strings are key-name syntax comments). Kept on purpose because Rust or the session spawn them: `matchbox-keyboard` and `alsa-utils` (amixer) (walpad-core daemon.rs), `xset`/`xsetroot` (session), `st` and `firefox-esr` (apps.json), `xkbcomp`/Xvfb deps. `xrandr xinput setxkbmap xrdb xclip` are unused by any shipped code but cost almost nothing and help SSH debugging, so they stay (change in one line if wanted).
- Files: after `cp -a config/rootfs`, `config/rootfs-nopython/apply.sh` deletes the paths in `REMOVE` (the six `walpad-*.py`, `walpad-keys-action`, the old shell `walpad-ctl` that talked to the Python devd, `walpad-python-daemons`) and copies `files/` over the tree. It then FAILS the build if any file coming from config/ still contains `python` or `.py` (only `walpad-runtime` is exempt, see below); the build also fails if /usr/bin/python* or wish exists or a python/py3/tk/tcl package is installed.
- Overlay files: `runtime.conf` = rust/rust/rust, shadow 0; `apps.json` without the Wi-Fi Tk app (Wi-Fi settings only exist in the Rust shell); `walpad-session`, `walpad-init` (identical to the default except the core block (rescue hook instead of Python daemons)); new `walpad-rust-check` and `walpad-rescue`.
- Default mode: `PKGS` and `config/rootfs` handling are unchanged. The only additions are the dry-run switch, `packages.txt`/`files.txt` written next to the image, and `mkdir -p "$OUT"` moved a few lines down. tests/shell asserts the default package list still has python3 tk py3-xlib xdotool and that the two lists differ by exactly those five.

## Capabilities and the guard (no Python to fall back to)
`walpad-runtime` is NOT changed and its guard is not weakened. In this image `walpad-rust-check` asks it for WALPAD_DEVICE, WALPAD_INPUT and WALPAD_SHELL and treats any answer other than `rust` (conf not rust, binary missing, capability missing, fell back this boot) as "unavailable", printing walpad-runtime's own reason (e.g. `WALPAD_SHELL unavailable: walpad-runtime: WALPAD_SHELL=rust ignored (walpad-shell lacks capability 'shell')`). The session then calls `walpad-rescue <reason>`; it never starts a launcher that is not there. (This is why `walpad-runtime` is the one script that still contains the word python: its `python` answer is the existing "refused" value.)

## What happens in each failure (exact)
The ramdisk (config/boot/init-os, unchanged) runs one check: if `/run/walpad-ok` does not exist 150 s after the chroot starts it kills Xvfb fbmirror openbox python3 st xterm firefox-esr and starts padui from `/bin/padui` in a restart loop. It never re-checks, and it does not kill walpad-core/walpad-shell. `walpad-rescue` (idempotent, first reason wins, flag dir `/run/walpad/rescue.d/`, reason in `rescue.d/reason`, also logged to /dev/kmsg as WALPAD-RESCUE) kills the supervisors, walpad-shell, walpad-core, matchbox-keyboard, firefox-esr, st, xterm, openbox, fbmirror and Xvfb, then:
- `/run/walpad-ok` missing (never healthy): does nothing more. The ramdisk starts padui at <=150 s after boot. The screen is blank until then. (A second padui must not be started: two framebuffer writers.)
- `/run/walpad-ok` present (the Rust shell drew its first frame, so the ramdisk already said "healthy" and will never fall back): starts padui from the rootfs copy `/usr/local/bin/padui` in a restart loop (`pidof padui` guard against duplicates), log /var/log/padui.log. walpad-core is stopped too, so padui alone handles keys/touch/screen.
After a rescue the session idles forever (init's `while true; walpad-session` therefore does not restart X on top of padui), and a later session start sees `rescue.d` and idles; /run is tmpfs so a reboot clears it.
Cases:
1. Rust shell lacks capability `shell` (today), binary missing, conf not rust, core lacks device/input: `walpad-rust-check` fails at the start of the session, before X starts, rescue with ok missing, padui at ~150 s.
2. Xvfb does not start: rescue, same as 1.
3. walpad-shell exits 3 times within 10 s (walpad-supervise): hook `walpad-rescue ...`; if it had drawn a frame, padui runs at once from the rootfs, otherwise padui at <=150 s via the ramdisk.
4. walpad-core exits 3 times within 10 s (supervised by init): same hook, same two sub-cases (there is no touch or power key without the core, so the shell is useless).
5. Shell hangs without ever drawing: ramdisk kills Xvfb at 150 s and starts padui; the session sees Xvfb gone with no walpad-ok, calls rescue (stops shell/core, no restart).
6. Xvfb dies after a healthy start: session exits 1, init restarts it after 3 s (same as the default image). If Xvfb is killed again by something and ok is gone the session goes to rescue.

## What a no-Python image can and cannot do until M5.9 flips the shell capability
`walpad-shell --capabilities` still prints nothing, so a no-Python image built today passes the guard for the core (device input) but fails for the shell: it boots to a blank panel, SSH and Wi-Fi (walpad-wifi) work, and padui takes the screen about 150 s after boot. That is the designed and tested outcome, not a usable UI. Reaching the Rust shell needs M5.9 (capability added after the owner's UI checklist) and a rebuild. I did not add an override for the capability on purpose. Nothing in this card was run on the tablet: padui-from-rootfs (chroot, /dev/fb0, input devices), walpad-rescue's pkill set and timing, and the blank 150 s are untested on hardware.
