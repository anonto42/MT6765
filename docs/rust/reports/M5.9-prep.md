Behaviour with WALPAD_SHELL=rust (read from walpad-runtime, walpad-session, walpad-supervise, shell.rs; not run on a device):
 - walpad-runtime returns rust only if: conf says rust, walpad-shell is on PATH, /run/walpad/fallback-shell does not exist, and `walpad-shell --capabilities` lists `shell`.  Otherwise it prints a reason to stderr and returns python (Tk launcher), so the session stays usable.
 - walpad-session then runs `walpad-supervise shell --require Xvfb -- walpad-shell` (log /var/log/walpad-shell.log), blocking.  The supervisor restarts the shell after 1 s each time it exits.  A run shorter than 10 s counts as a quick exit; 3 quick exits in a row write /run/walpad/fallback-shell and the supervisor returns; the session logs "Rust shell failed 3 times: using the Tk launcher until reboot" and `exec walpad-launcher.py`.  A run of 10 s or more resets the counter.  If Xvfb is gone the supervisor exits 3 and the session exits 1 (restart the session).  The fallback flag lives in /run, so the next boot tries Rust again.
 - /run/walpad-ok is removed at session start and written by the shell (shell.rs) after its first presented frame.  A shell that crashes before its first frame never writes it; the init health check then sees an unhealthy session and uses the padui rescue (as with any broken session).  The Tk launcher fallback writes its own ok as before.  Note: a shell that stays up but paints nothing would not be fallen back (no quick exit) - that is the case to look for on the device.
