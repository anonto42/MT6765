## What works now (M8.1, host-verified only)
- fbmirror reads /run/walpad/status.json (open, fstat, read, close, plus one clock_gettime) at most every 250 ms while copying. If it is fresh (mtime within 10 s of now, either direction) and has the key `"screen"` with the value exactly `"off"`, fbmirror enters a paused state: no comparison, no copy, no pan, no rotation read; it only sleeps 200 ms and re-reads status.json each loop (so it resumes within 200 ms plus the read, i.e. one poll).
- `on`, `dim`, key missing, file missing, file unreadable, truncated, stale, clock jump: keep copying exactly as before (copy loop and the 40 ms sleep are unchanged).
- On resume it clears the shadow copy, forces `inited = 0` and re-reads the orientation, so the next pass does one full copy into the hidden page and one pan. Panel wake (`blank` 1 then 0, once), pan, double buffering and the rotation handling (no blanking, 300 ms settle) are untouched. A rotation that happens while paused is picked up on resume.
- Expected CPU effect (an expectation, not a measurement): while off, about 5 syscalls per 200 ms instead of reading ~1 M pixels every 40 ms.
- Logic lives in `tools/fbmirror/logic.h` (freestanding, no includes, no libc): `fb_parse_screen_off`, `fb_status_off` (freshness), `fbgate` + `gate_poll_due` / `gate_update` / `gate_sleep_ms`. `tools/fbmirror/test_logic.c` tests about 40 assertions (parser incl. whitespace, `"screen"` appearing as a value, `screen_x`, truncation; freshness; poll cadence; pause/resume/refresh transitions).
- Binary: `file` says `ELF 64-bit LSB executable, ARM aarch64, version 1 (SYSV), statically linked, ... not stripped`; size 5.0 KB (ls: 5.0k) built by `tools/fbmirror/build.sh` (docker, clang, freestanding). The binary is a build output, not committed.
- aarch64 specifics used and NOT verified on hardware: `struct stat` st_mtime.tv_sec at byte offset 88 (read as u64 index 11 of a 144-byte buffer); `clock_gettime` = syscall 113 with CLOCK_REALTIME. If the offset were wrong the age check would fail and fbmirror would simply keep copying (safe direction), so the first device check is that the pause actually happens.

5. `dim` state: the picture keeps updating while dimmed.

## M8.2 measurement: scripts/device/measure_fbmirror.sh
Run on the tablet as root, with nobody touching it (about 130 s): `ssh root@<ip> sh -s < scripts/device/measure_fbmirror.sh` (env `DURATION=60`). It finds fbmirror, sets `screen on`, waits 5 s, samples /proc/<pid>/stat utime+stime for 60 s (CPU idle), then sends `screen off` through /run/walpad/devd.cmd, waits 5 s, samples 60 s again, and always sends `screen on` at the end (also on Ctrl-C). Output is a table (phase, screen state read from status.json, ticks, seconds, CPU %) and the verdict line `M8.2 needed: yes/no (threshold 5% of one core with the screen on)`.
How to read it:
- `screen_off` near 0 % with the new binary: M8.1 works. With the old binary (or if the pause does not trigger) screen_off is about equal to screen_on: then M8.1 is not effective, investigate (step 2/6 above).
- The verdict only looks at the screen-on idle number. `yes` (above 5.0 %) means the 40 ms full-frame compare is a real cost and M8.2 (damage-driven mirror) is worth doing; `no` means leave M8.2 out. The idle test should be run with the Rust shell showing a static page (no animation) or it measures the animation.
- If the `screen` column says `unknown` or the wrong state, that phase is invalid (devd not running, or the command FIFO is missing).
- Note the script measures only fbmirror, not Xvfb. Xvfb CPU while idle is a separate question for M8.2 if the number is high.

## M8.3 measurement: scripts/device/measure_firefox_mem.sh
Run on the tablet as root with Firefox closed: `sh measure_firefox_mem.sh [url ...]` (about 4 x 50 s). For four configurations A defaults, C low-memory prefs, B defaults + zram, D low-memory prefs + zram, it starts `firefox-esr --headless` on a throw-away profile with 3 pages, waits `WAIT` seconds (40) and records the number of firefox processes, the summed VmRSS of the process tree, MemAvailable and swap used. It sets the same software-rendering/sandbox environment as walpad-session. It refuses to run if another firefox is running (`ALLOW_RUNNING=1` overrides). Changes are limited to a temporary zram swap (`ZRAM_MB` 512, `lz4`, only if zram0 is unconfigured and no swap exists) and /tmp files; everything is undone on exit.
Default pages are three generated local pages (60 000 DOM nodes and a 1.5 M element array each): a synthetic load, not a real site. Pass real URLs as arguments (needs Wi-Fi) for numbers that matter; do the run once with the sites the owner actually uses.
How to read it: MemAvailable_MB is the number to compare (higher is better; RSS over-counts shared pages). Compare A vs B for zram, A vs C for the prefs, D for both. Treat differences under about 5 % as noise (run twice). Decision rule suggested: adopt zram if B or D raise MemAvailable and the swap used stays well below the zram size without the UI becoming slow; adopt the prefs only if C saves a clearly visible amount (for example more than 100 MB) and pages still render. If both are marginal on 4 GB, change nothing.

## Recommended defaults to try (UNTESTED, NOT in the image)
These are starting points taken from general Firefox ESR knowledge. None of them was run on this tablet or checked against the installed Firefox ESR version; pref names can be ignored by a given version. The measurement script uses exactly this set for configurations C and D (the heredoc `lowmem.js`).
Low-memory prefs, to be placed as `user.js` in a profile (the owner decides where; not added by me):
```
user_pref("dom.ipc.processCount", 1);
user_pref("dom.ipc.processCount.webIsolated", 1);
user_pref("fission.autostart", false);
user_pref("browser.cache.memory.capacity", 16384);
user_pref("browser.sessionhistory.max_total_viewers", 0);
user_pref("browser.tabs.unloadOnLowMemory", true);
user_pref("javascript.options.mem.high_water_mark", 64);
user_pref("image.mem.decode_bytes_at_a_time", 32768);
user_pref("gfx.canvas.accelerated", false);
user_pref("media.memory_cache_max_size", 8192);
user_pref("extensions.pocket.enabled", false);
user_pref("browser.startup.homepage", "about:blank");
```
Risks: fewer content processes means a crashing page takes more tabs with it; `max_total_viewers 0` makes Back slower; `fission.autostart=false` may be ignored or unsupported on newer ESR builds.
zram, untested manual setup (as root, once per boot; the kernel config lists zram as enabled but nobody has checked that /dev/zram0, lz4 and swapon work on this 4.19.127 kernel):
```
echo lz4 > /sys/block/zram0/comp_algorithm      # may fail: then skip, default algorithm is fine
echo 1G > /sys/block/zram0/disksize             # 512M to 1G on 4 GB RAM; write 1073741824 if the kernel rejects "1G"
mkswap /dev/zram0 && swapon -p 100 /dev/zram0
echo 100 > /proc/sys/vm/swappiness              # optional: prefer zram over dropping file cache; the default 60 is also fine
```
Undo: `swapoff /dev/zram0; echo 1 > /sys/block/zram0/reset`. To make it permanent the owner would add it to the session or an init script in a later card, after the measurement shows a benefit; I did not.

## Deviations
- The worktree started on an old commit; I fast-forwarded it to main (d291ee5) to get docs/rust and scripts/check.sh before working. No history was rewritten.
- The 250 ms status poll is a count of slept milliseconds, not a wall-clock timer, so it is slightly slower than 250 ms when a frame copy takes long; irrelevant for the on-state, and the paused state polls every 200 ms.
- The pause decision uses the file mtime against the wall clock: if the tablet's clock jumps by more than 10 s while the screen is off, fbmirror resumes copying until the next fresh poll (safe direction, a few wasted frames).
- No Rust changes; TASKS.md untouched (as instructed).

## Rollback
`git revert` the M8 commit, rebuild tools/fbmirror with build.sh, and rebuild/flash only if the new binary had been deployed. On a running tablet, put the previous fbmirror binary back and restart it, or reboot. The measurement scripts change nothing persistent; if one was killed with SIGKILL, run `swapoff /dev/zram0; echo 1 > /sys/block/zram0/reset` and `rm -rf /tmp/walpad-ffmem.*`.
