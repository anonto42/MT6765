# M3.1 runtime.conf handling, core restart loop, auto-fallback
Status: done on the host; takes effect on the tablet only after a rootfs rebuild + flash (owner approval) or by copying the scripts over SSH
Files changed: config/rootfs/usr/local/sbin/{walpad-runtime,walpad-supervise,walpad-python-daemons}, config/rootfs/sbin/walpad-init, config/rootfs/usr/local/sbin/walpad-session, crates/walpad-{core,shell}/src/main.rs (--capabilities), tests/shell/run.sh, scripts/check.sh
What works now:
 - walpad-runtime KEY resolves python|rust from /etc/walpad/runtime.conf. `rust` is honoured only if the binary exists, reports the capability (`walpad-core --capabilities` must list device/input, `walpad-shell --capabilities` must list shell) and has not fallen back this boot. Garbage or a missing file means python.
 - walpad-supervise NAME [--require PROC] [--on-fallback CMD] -- cmd: restart loop; 3 exits under 10 s in a row -> writes /run/walpad/fallback-NAME, runs the hook once, stops. /run is tmpfs, so "until the next boot".
 - walpad-init starts walpad-core in its own supervised loop only when device/input is rust or shadow=1; on core fallback the matching Python daemons are started.
 - walpad-session starts only the Python daemons for subsystems that are still python, and runs a Rust shell in its own loop (X is not restarted when the shell crashes; X dying ends the session so init restarts it). 3 quick shell exits -> Tk launcher.
 - With the default runtime.conf (all python, shadow 0) the boot sequence is the same as before.
Safety guard (deviation, intentional): the core and shell report NO device/input/shell capability yet (core: "ipc shadow"), so even WALPAD_DEVICE=rust is ignored today. M3.2/M3.3 add the capabilities, M5 adds `shell`. Without this, setting rust now would leave the tablet with no screen timeout, power key or touch.
